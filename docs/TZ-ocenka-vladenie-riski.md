# Оценка п.7 — позиция Исполнителя (владение, безопасность, коммерческие границы)

**Документ:** Аннекс Исполнителя — оценка полноты и коммерческой сбалансированности пункта 7 ТЗ Заказчика  
**Назначение:** зафиксировать пробелы формулировок п.7 для сбалансированной приёмки и снижения рисков **обеих** сторон; предложить редакцию и границы объёма при фиксе 370 000 ₽/мес  
**Статус:** рабочий аннекс **Исполнителя** (не правка вкладок Заказчика)  
**Дата:** 2026-07-18  
**Предмет:** система учёта и операционного контура («Учёт №1»)  
**Позиция:** Исполнитель (дополнение к ТЗ Заказчика)

Настоящий текст — **дописывание позиции Исполнителя** отдельной вкладкой. Вкладки Заказчика («Не учтено в ТЗ», основное ТЗ, стек, аналитика и др.) данным документом **не изменяются**.

Документ не оспаривает право Заказчика на владение инфраструктурой, контроль платежей и требование передаваемости. Документ фиксирует, какие условия п.7 в текущей редакции **недостаточно специфицированы** для честной приёмки, содержат **скрытую стоимость** либо создают **структурный дисбаланс** при модели «фикс 370 тыс. ₽/мес / команда ~3 FTE / вся разработка».

**Классификация в тексте:**
- **нормальная практика** — соответствует рынку B2B-внедрений;
- **перекос** — формулировка смещает риски/объём на одну сторону без компенсации;
- **скрытая стоимость** — требование выглядит «бесплатным дополнением», фактически требует отдельного объёма часов / ops / подрядчика.

## 2. Разбор каждой строки п.7

### 2.1. «Код — в репозитории Заказчика; инфраструктура и домены — у Заказчика»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Размещение кода и инфра у Заказчика — стандарт для снижения vendor lock-in. |
| **Перекос / пробел** | «Код в репо» **не** определяет режим прав: исключительные права, простая/исключительная лицензия, момент перехода прав, судьба заготовок Исполнителя, open-source зависимости, сторонние SDK. |
| **Скрытая стоимость** | Миграция в репо Заказчика, настройка CI, секреты, доступы, code review process — отдельный объём (часто Э0), если не выделен явно. |

**Вывод.** Требование владения инфраструктурой — легитимно. Без блока IP / лицензии приёмка «владения» юридически неопределённа: доступ к git ≠ уступка исключительных прав.

### 2.2. «Полная инструкция развёртывания с нуля»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Runbook / deploy-from-scratch — обязательный артефакт для передаваемости. |
| **Перекос / пробел** | Не заданы: целевая ОС, версии runtime, минимальные ресурсы, состав секретов, эталонные команды, критерий «успешно поднято», кто предоставляет staging. |
| **Скрытая стоимость** | Поддержание актуальности инструкции при каждом релизе — непрерывная работа (docs debt), не разовое «написать README». |

### 2.3. «Сторонний разработчик по документации поднимает копию системы»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Transferability test — сильный критерий зрелости поставки. |
| **Перекос** | Не указано: кто нанимает и оплачивает стороннего; лимит часов; квалификация; среда (чьи серверы); критерий «поднял» (healthcheck / smoke / полный функционал); сколько итераций правок docs входит в цену. |
| **Скрытая стоимость** | Без лимита это открытый чек: Исполнитель бесконечно чинит docs под чужой опыт, плюс оплата внешнего специалиста. |

**Вывод.** Тест передаваемости должен быть **оплачиваемым этапом** с DoD, либо фиксированным пакетом часов в рамках приёмки финального этапа / Э0.

### 2.4. «Ежедневные бэкапы + ежемесячный тест восстановления»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Backup + restore-drill — базовая эксплуатационная дисциплина. |
| **Перекос** | В п.7 сформулировано как требование к **поставке разработки**, тогда как это **операционная услуга** (SRE/ops), длящаяся месяцами. |
| **Скрытая стоимость** | Автоматизация бэкапов, хранение, шифрование, отчётность, ежемесячный drill с протоколом — отдельный SLA-контур. Не заданы RPO/RTO, владелец бэкапов, место хранения, кто подписывает акт restore. |

### 2.5. «Логи действий пользователей — не менее года»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Audit trail для складского/финансового контура — ожидаемо. |
| **Перекос / пробел** | Нет: модель событий (что логируем), объём роста, формат хранения, стоимость диска, purge/архивация, доступ на чтение, PII/152-ФЗ. |
| **Скрытая стоимость** | Год хранения при высокой активности склада/оплат — инфраструктурный и продуктовый объём (схема, индексы, ретеншн, UI просмотра). |

### 2.6. «Доступы по ролям, 2FA для админов»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | RBAC + MFA для привилегированных учёток — рынок. |
| **Перекос / пробел** | Нет политики: какие роли = «админ»; исключения для складских iPad/shared devices; recovery codes; IdP; стоимость внедрения в этапе Э0 vs отдельно. |
| **Скрытая стоимость** | MFA (TOTP/WebAuthn), enrollment, support сброса 2FA — продукт + поддержка, не «галочка в ТЗ». |

### 2.7. «Платежи из банка — только с одобрения Заказчика (зафиксировано 17.07.2026)»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Бизнес-контроль исходящих платежей — корректное требование владельца средств. |
| **Пробел (не враждебный)** | Нужны границы API/автоматизации: что может система без человека; что требует явного approve; журнал решений; ответственность за ручной обход. |
| **Скрытая стоимость** | Workflow approve, уведомления, роли, аудит — отдельный функциональный объём, если ещё не в этапе. |

### 2.8. «Документация и передаваемость — часть приёмки КАЖДОГО этапа»

| Оценка | Комментарий |
|--------|-------------|
| **Нормальная практика** | Docs-as-acceptance снижает риск «потом разберёмся». |
| **Перекос** | Без **шаблона DoD документации** и лимита объёма артефактов приёмка становится бесконечной: любой этап можно не принять со ссылкой на «недостаточно передаваемо». |
| **Скрытая стоимость** | При 3 FTE доля времени на docs/KT может съесть 20–40% ёмкости месяца — если не зарезервирована в capacity model, «вся разработка» физически не помещается. |

## 3. Обязательный реестр пробелов (для честной приёмки п.7)

Без закрытия пунктов ниже формулировки п.7 **не пригодны** как критерии приёмки этапа (неопределённый объём / неопределённый успех).

### 3.1. Интеллектуальная собственность и режим прав (IP)

- [ ] Режим прав на результат работ: **исключительные права** Заказчику **после полной оплаты этапа** **или** **неисключительная/исключительная лицензия** с перечнем ограничений.  
- [ ] Явно: «размещение в репозитории Заказчика» ≠ автоматическая уступка исключительных прав до оплаты.  
- [ ] Судьба **заготовок, библиотек, шаблонов Исполнителя**, использованных в проекте (сохранение права Исполнителя на переиспользование в обезличенном виде).  
- [ ] Open-source / third-party зависимости: перечень лицензий, запрет GPL-incompatible если требуется, ответственность за compliance.  
- [ ] Момент передачи: после акта и оплаты; escrow-релиз при споре (см. 3.8).

### 3.2. Тест передаваемости (сторонний разработчик)

- [ ] Кто **оплачивает** стороннего разработчика (Заказчик по умолчанию).  
- [ ] Лимит: N часов (рекомендуется 8–16 ч на финальный тест; повторные прогоны — по change request).  
- [ ] Квалификация: backend PHP/Node + Linux + SQL (уточнить под стек этапа).  
- [ ] Среда: staging на инфраструктуре Заказчика; доступы выдаёт Заказчик.  
- [ ] Критерий успеха: система отвечает на healthcheck; выполнен согласованный smoke-checklist (не «весь прод»).  
- [ ] Исправление документации по результатам теста: фиксированный пакет часов в объёме этапа.

### 3.3. Документация на каждом этапе — Definition of Done

Минимальный комплект на этап (шаблон):

- [ ] Changelog этапа (что сделано / что не вошло).  
- [ ] Обновление runbook развёртывания **только по затронутым контурам**.  
- [ ] Список новых env/секретов.  
- [ ] Краткая схема интеграций этапа (если менялись).  
- [ ] Чеклист smoke для приёмки этапа (10–20 пунктов).  

**Вне scope фикс-месяца без отдельной оценки:** видеокурс, обучение штата Заказчика, полное «учебное пособие», повторная сертификация сторонним без лимита часов.

### 3.4. Бэкапы и ежемесячный restore-drill (ops, не «разработка»)

- [ ] RPO / RTO (целевые значения).  
- [ ] Что бэкапится: БД / файлы / конфиги / секреты (политика секретов отдельно).  
- [ ] Владелец хранения бэкапов: Заказчик.  
- [ ] Отчётность: ежемесячный протокол restore (дата, объём, результат, время восстановления).  
- [ ] Входит ли ops в 370 тыс. или оформляется отдельным SLA (рекомендация: **отдельная строка** или явный % ёмкости, см. §5).

### 3.5. Audit log ≥ 1 год

- [ ] Матрица событий аудита (login, смена роли, финансовые операции, складские критичные действия, экспорт).  
- [ ] Срок online vs cold storage; политика purge.  
- [ ] Оценка объёма и стоимости хранения.  
- [ ] UI/API доступа к журналу и роли читателя.

### 3.6. RBAC + 2FA

- [ ] Политика MFA: обязательна для ролей Admin / Finance / …  
- [ ] Исключения: складские shared iPad (device-bound session / PIN / без MFA — явно).  
- [ ] Процедура сброса 2FA (кто утверждает).  
- [ ] Объём внедрения: этап Э0 / отдельная смета.

### 3.7. Одобрение банковских платежей

- [ ] Граница автоматизации API банка: read-only выписки vs init payment.  
- [ ] Обязательный human-approve для исходящих; журнал approve/reject.  
- [ ] Запрет обхода через прямые токены вне системы (ответственность сторон).

### 3.8. Заменяемость Исполнителя (replaceability) без «односторонней утилизации»

При отсутствии ниже Исполнитель структурно disposable mid-flight при полном раскрытии знаний:

- [ ] **Notice period** расторжения (рекомендуется ≥ 30 календарных дней) + оплата WIP по факту.  
- [ ] Переход исключительных прав / полный IP-пакет — **только после полной оплаты** принятых этапов.  
- [ ] **Paid knowledge transfer** (KT): фиксированный пакет часов при смене подрядчика.  
- [ ] **Access matrix**: кто имеет prod/admin; отзыв доступов Исполнителя по процедуре.  
- [ ] Опционально: **source escrow** / dual-control на критичные секреты.

### 3.9. Модель ёмкости 370 000 ₽/мес / ~3 FTE

- [ ] Явная таблица: % feature development / % bugs&support / % docs&KT / % ops&security.  
- [ ] Change control: новый scope («ещё и вся разработка по ТЗ») → оценка → сдвиг срока или доп. бюджет.  
- [ ] Запрет подразумевать, что фикс-месяц = весь бэклог ТЗ Э0–Э5.

## 4. Рекомендуемые формулировки (редакция п.7 / доп. соглашение)

Ниже — текст для согласования сторонами (черновик). Имена сторон: **Заказчик**, **Исполнитель**.

### 4.1. Владение кодом и инфраструктурой

«Исходный код результата работ по принятым и оплаченным этапам размещается в репозитории Заказчика. Инфраструктура, домены и прод-доступы принадлежат Заказчику. Режим прав на РИД (исключительные права / лицензия), момент перехода и исключения для заготовок Исполнителя и open-source зависимостей определяются в договоре / приложении об IP. Размещение кода в репозитории само по себе не означает перехода исключительных прав до подписания акта и оплаты соответствующего этапа.»

### 4.2. Документация и развёртывание

«В состав приёмки каждого этапа входит комплект документации по согласованному шаблону DoD (changelog, затронутые разделы runbook, секреты/env, smoke-checklist). Полная инструкция „с нуля“ поддерживается в актуальном состоянии в объёме затронутых контуров этапа; полная перепись документации „всего продукта“ — отдельная работа.»

### 4.3. Тест передаваемости

«Один раз на согласованный этап (рекомендуется финал Э0 или закрытие пилота) Заказчик организует проверку: сторонний разработчик по документации поднимает копию на staging Заказчика. Оплату стороннего несёт Заказчик. Лимит сопровождения Исполнителем — N часов (согласовать). Критерий успеха — согласованный smoke-checklist. Повторные проверки и сверхлимитные часы — по дополнительному соглашению.»

### 4.4. Бэкапы и restore

«Ежедневные бэкапы и ежемесячный тест восстановления относятся к операционному контуру. Параметры RPO/RTO, место хранения и формат отчётности фиксируются в SLA эксплуатации. Включение ops в ежемесячный фикс либо выделение отдельной строки бюджета — предмет согласования capacity (§5).»

### 4.5. Audit / RBAC / 2FA

«Ролевая модель и MFA для привилегированных ролей внедряются в объёме этапа Э0 (или отдельной сметой). Политика исключений для складских устройств, матрица событий аудита и ретеншн ≥ 1 год фиксируются приложением „IAM / Audit“. Хранение и стоимость cold storage — ответственность владельца инфраструктуры (Заказчик), реализация схемы аудита — Исполнитель в согласованном объёме.»

### 4.6. Платежи банка

«Инициирование исходящих платежей из банковского API допускается только после явного одобрения уполномоченным лицом Заказчика. Границы автоматизации (чтение выписок, статусы, webhooks) и журнал решений фиксируются в ТЗ оплат.»

### 4.7. Прекращение / замена подрядчика

«При расторжении по инициативе Заказчика: уведомление не менее чем за 30 дней; оплата фактически выполненных и принятых работ / WIP по согласованной оценке; передача полного комплекта доступов и документов в рамках paid KT (пакет часов). Переход исключительных прав на неоплаченный результат не производится. Стороны содействуют непрерывности сервиса без ущерба коммерческим интересам друг друга.»

## 5. Границы объёма при фиксе 370 000 ₽/мес (~3 FTE)

Ориентир ёмкости: **~480–520 чел.-часов/мес** (3 FTE × ~160–170 ч). Без явного резерва «документация + ops + поддержка» требование «вся разработка + п.7 целиком» **математически несовместимо** с фиксом.

### 5.1. Рекомендуемая раскладка ёмкости (для согласования)

| Контур | Доля | Что входит |
|--------|------|------------|
| Feature development (этап по дорожной карте) | 55–65% | Согласованный scope спринта/этапа |
| Bugs, prod support, мелкие правки | 10–15% | В пределах SLA ответа |
| Документация этапа + внутренний KT | 10–15% | По шаблону DoD §3.3 |
| Ops / backups / мониторинг / security hygiene | 5–10% | Только если ops **включён** в фикс |
| Резерв / buffer | 5–10% | Риски, инциденты |

### 5.2. Что входит в фикс (при условии согласования этапа)

- Разработка и поставка **согласованного** scope этапа.  
- Документация этапа по шаблону DoD.  
- Размещение кода в репо Заказчика в рамках процесса поставки.  
- Базовая ролевая модель в объёме этапа (если этап = Э0 — по смете Э0).

### 5.3. Что отдельно (или отдельной строкой / % ёмкости)

| Позиция | Почему отдельно |
|---------|-----------------|
| Ежемесячный restore-drill + отчётность SLA | Ops, не feature |
| Оплата стороннего разработчика на transferability test | Заказчик / внешний подряд |
| Сверхлимитное сопровождение теста передаваемости | Change request |
| Полный MFA/IAM продукт (enrollment, recovery, device policy) | Если не умещен в Э0 |
| Год online hot-storage аудита сверх базовой схемы | Инфра Заказчика + объём реализации |
| Source escrow / нотариальный deposit | Юр. услуга |
| Paid KT при смене подрядчика | Отдельный пакет |
| Обучение штата Заказчика / видеокурс | Не передаваемость кода |
| «Вся разработка по полному ТЗ Э0–Э5» в одном месяце | Вне ёмкости; нужна дорожная карта |

### 5.4. Change control

Любое требование вида «ещё и …» сверх согласованного backlog месяца оформляется: оценка часов → приоритет (вытеснение другой задачи) **или** доп. бюджет / сдвиг срока. Устное «это же из п.7» без DoD **не** расширяет объём.

## 6. Риски Исполнителя и митигации

| Риск | Проявление | Митигация |
|------|------------|-----------|
| Односторонняя заменяемость | Полный KT + код у Заказчика → смена подрядчика mid-flight без оплаты WIP | Notice 30+, оплата WIP, IP после оплаты, paid KT |
| Бесконечная приёмка docs | «Передаваемость» без DoD | Шаблон артефактов на этап; чеклист |
| Скрытый ops в цене разработки | Backups/restore как «часть ТЗ разработки» | Выделить SLA ops; % ёмкости |
| Перенос IP до оплаты | Репо Заказчика с day one + спор | Лицензия на период работ; уступка после акта/оплаты |
| Transferability за счёт Исполнителя | Стороний тестировщик + безлимитные правки | Оплата внешнего Заказчиком; лимит часов |
| Размытие 370к | «Вся разработка» + п.7 + поддержка | Capacity table; change control |
| Prod-доступ без процедуры | Личная ответственность за инциденты | Access matrix; dual control; журнал |
| 2FA без исключений склада | Блок операционки iPad | Политика устройств в ТЗ IAM |

**Принцип баланса:** Заказчик получает непрерывность, контроль платежей, код и инфра у себя, проверяемую передаваемость. Исполнитель получает определённый объём, определённую приёмку, оплату результата и защиту от безвозмездной утилизации mid-flight.
