# Схема учёта применимости: каталог vs партия

## Задача

Один артикул в каталоге может подходить на несколько марок (Audi / Bentley / Porsche).
Поставщики делают партии, которые физически годятся только на часть авто.
Менеджеру и складу нужно видеть **куда годится именно эта штука**, не путая с максимумом каталога.

## Уровни (от широкого к узкому)

```
1. Каталог: product_applicability
   «товар вообще бывает на эти авто» (максимум)
        │
2. Поставщик × товар: supplier_product_apps
   дефолт «обычно от этого поставщика — такие марки»
        │
3. Строка прихода: stock_doc_lines.apps_json
   явное указание при оприходовании партии
        │ копируется на экземпляры
4. Экземпляр: product_units.apps_json  ← источник правды
   пустой [] = без урезания (как каталог)
        │ проверка при скане
5. Строка заказа: crm_deal_items.mark / model / generation
   скан марки отклоняется, если партия не подходит
```

## Правило разрешения при приходе

При проведении прихода / возврата для каждой создаваемой марки:

1. Если в строке документа задан `apps_json` — берём его.
2. Иначе, если есть дефолт `supplier_product_apps` (поставщик шапки × товар строки) — берём его.
3. Иначе `[]` — экземпляр без доп. ограничения (менеджер опирается на каталог).

Код: `resolveAppsForReceive` в `api/src/applicability-party.ts`.

## Правило проверки при скане в заказ

`POST /crm/deals/:id/scan-unit` → `assignDealUnitByScan`:

- Совпадает артикул / SKU с позицией заказа.
- Если у строки заказа указаны марка/модель (авто клиента) **и** у экземпляра `apps_json` не пустой — партия должна покрывать это авто.
- Если у экземпляра apps пустые — не блокируем (каталог).
- Если в заказе авто не указано — не блокируем.

## Формат `apps_json`

Массив объектов:

```json
[
  { "mark": "Audi", "model": "", "generation": "", "years": "" },
  { "mark": "Porsche", "model": "Cayenne", "generation": "", "years": "" }
]
```

В UI прихода / карточки марки можно передать строку `"Audi, Bentley"` — парсер развернёт в объекты с марками.

## API

| Метод | Путь | Назначение |
|-------|------|------------|
| PATCH | `/product-units/apps` | `{ serial, apps }` — править применимость экземпляра |
| GET | `/supplier-product-apps?product_id=&supplier_id=` | дефолт поставщика |
| PUT | `/supplier-product-apps` | `{ product_id, supplier_id, apps }` |
| POST | `/docs` | в строках можно передать `apps` |
| POST | `/crm/deals/:id/scan-unit` | проверка + ответ с `apps_label` |

Ответы экземпляров (`/product-units`, `/product-units/trace`) отдают `apps`, `apps_label`, `apps_short`.

## Как учитывать в работе

1. **Номенклатура** — применимости каталога как сейчас (HS / карточка товара): «куда товар бывает».
2. **Приход** — поле «Применимость партии»: куда годится **эта** поставка. Если не указать — подставится дефолт поставщика или останется «как в каталоге».
3. **Поставщик × товар** — зафиксировать типичное урезание (`PUT /supplier-product-apps`), чтобы не вбивать на каждом приходе.
4. **Карточка марки** — посмотреть / поправить применимость партии после прихода.
5. **Заказ покупателя** — указать авто в позиции; при скане склад не привяжет чужую партию.
6. **Выбор партии в сделке** — в списке приходов показывается короткая метка марок (`AU+PO`).

## Чего схема намеренно не делает

- Не дробит артикул в каталоге на «Audi-SKU» / «Porsche-SKU».
- Не подменяет применимости каталога данными партии.
- Не требует apps на старых экземплярах (пусто = каталог, обратная совместимость).
