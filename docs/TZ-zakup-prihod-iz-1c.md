# ТЗ · Закуп + Приход (паритет с 1С по скринам)

**Продукт:** Учёт №1 (WMS)  
**Источник требований:** скрины процесса 1С (заказ поставщику MRA-3 / 00НФ-000032, Excel-загрузка, анализ заказа, приход на основании)  
**Дата:** 2026-09-01  
**Статус:** к реализации  

---

## 0. Цель

Повторить рабочий контур закупщика и склада из 1С **без потери шагов**:

1. Закупщик заливает таблицу (копипаст / Excel) в **заказ поставщику** с ценами.
2. Создаёт недостающие карточки номенклатуры (в т.ч. новый артикул + кросс со старого).
3. Проводит заказ → статус **«В пути»**, сообщает складу **номер заказа**.
4. Склад принимает товар **на основании заказа** → **приходная накладная** (черновик → факт → проведение).
5. Закупщик / склад видит **Анализ заказа**: Заказано / Получено / Осталось (остаток может быть **отрицательным** = излишек).

**Не цель этого ТЗ:** полный паритет всех пунктов меню 1С (счета поставщика, ГТД, доп. расходы и т.д.) — только цепочка со скринов.

## 3. Статусы заказа (жизненный цикл)

Как на скринах журнала: `В пути`, `Завершен`, и проведение.

| Статус | Когда | Кто |
|--------|-------|-----|
| `draft` · Черновик | Создан, строки редактируются | Закупщик |
| `posted` / `confirmed` · Проведён | Нажали «Провести» / «Провести и закрыть» (без отправки на склад ещё можно оставить) | Закупщик |
| `in_transit` · **В пути** | Проведён **и** отдан складу (или сразу при «Провести и закрыть» с ETA) | Закупщик |
| `partial` · Частично получен | Есть ≥1 проведённый приход по заказу, но осталось > 0 по сумме qty | Система |
| `received` · Получен | Осталось получить ≤ 0 по всем строкам (или закрыто вручную) | Система / закупщик |
| `closed` · Завершён | Ручное закрытие или полный приход | Закупщик |
| `cancelled` | Отмена | Закупщик |

**UI:** в карточке заказа кнопки как в 1С:
- **Записать** (сохранить без смены статуса)
- **Провести** → `posted` (или сразу `in_transit` — выбрать один UX, зафиксировать: **рекомендация = «Провести и закрыть» → `in_transit`**)
- **Провести и закрыть** → `in_transit`, закрыть карточку, номер виден в журнале для склада

В журнале колонка статуса с бейджем (как сейчас thinStatusBadge + добавить `in_transit` → «В пути»).

## 4. Импорт в заказ (Excel / копипаст) — ядро закупа

### 4.1. Точка входа (как на скрине)

В карточке **Заказа поставщику** → вкладка номенклатуры → кнопка:

**«Заполнить из внешнего источника»**

Открывает мастер (модалка / пошаговый экран), аналогично 1С «Загрузка данных из Excel».

### 4.2. Шаг 1 · Способ

Два варианта (оба обязательны):

1. **Загрузить файл** `.xlsx` / `.csv`
2. **Заполнить таблицу самостоятельно** (предпочтение со скрина: «мне удобнее копипастом»)  
   Текст: «Скопируйте строки (Ctrl+C) и вставьте (Ctrl+V) в таблицу на следующем шаге»

### 4.3. Шаг 2 · Маппинг колонок

Дефолтный шаблон (сохраняемый), как на скрине:

| Колонка источника | Поле Учёта | Обязательно |
|-------------------|------------|-------------|
| 1 | **Артикул** | да |
| 2 | **Количество** | да |
| 3 | **Цена** | да для заказа |
| 4 | **Сумма** (или «Сумма НДС» в 1С-маппинге — у нас трактовать как **сумма строки** = qty×price; если пришла сумма — можно пересчитать цену = сумма/qty) | нет |
| 5+ | **Не загружать** / **Старый артикул** | опционально |

Дополнительно в шаблоне (для пакинга со скрина):

| Колонка | Поле |
|---------|------|
| Старый номер / кросс | `old_sku` → в карточку `warehouse_sku` + `array_sku` |

Кнопки как на скрине:
- Сохранить настройки
- Загрузить настройку из файла
- Выбрать настройку из шаблона («Заказ поставщику · пакинг»)

### 4.4. Нормализация артикулов

Со скрина: в буфере бывают `AE12679`, `AA20460` без префикса `MR`.

Правила (в порядке):
1. Trim, upper, убрать пробелы.
2. Если артикул вида `^[AE]{2}\d{5}$` или `^A[AE]\d{5}$` без `MR` — пробовать префикс **`MR`** (`AE12679` → `MRAE12679`).
3. Поиск: `sku` → `code` → `array_sku` → `warehouse_sku` (как сейчас в матчинге).
4. Предпочитать активный бренд **MRAER**, без `@podveska` и без `:clone`.

### 4.5. Шаг 3 · Сопоставление (как на скрине анализа)

Показать сводку:

- **N строк получено**
- **M из них сопоставлено**
- **K строк будет создано**
- **E невозможно загрузить**

Чекбоксы:
- ☑ **Создавать новые элементы, если не сопоставлены**
- ☐ Обновлять сопоставленные элементы полученными данными (по умолчанию **выкл** — как на скрине)

Список проблемных строк с фильтром «Ошибка / будет создан»:
- артикул
- статус: «Будет создан новый элемент» / «Не найден источник для клона» / «Нет qty»

### 4.6. Создание новых карточек (3 кейса со скрина)

Правила (зафиксировать из практики Supplier X + скрины):

| Ситуация | Действие |
|----------|----------|
| Артикул **по факту** найден | Брать эту карточку |
| Есть **старый артикул**, факта нет / нужна новая | Создать карточку со **sku = факт**; скопировать с карточки **старого** (или ближайшего аналога): название, категория, применимость, фото, цены продажи, свойства, габариты; в `array_sku` и `warehouse_sku` добавить старый |
| Нет ни факта, ни старого, но есть близкий аналог (серия MRAA21118→MRAA21718) | Клон с ближайшего sibling по правилам маппинга (таблица аналогов или ручной выбор в UI) |
| Создавать «без кроссов и розницы» (как сказал закупщик на скрине) | Режим импорта: **«Минимальная карточка»** — sku, name (из соседней/placeholder), brand MRAER, category; без копирования цен/медиа. Флаг в мастере. |

После создания — повторный матч; цель: **0 невозможно загрузить** перед «Загрузить данные».

### 4.7. Шаг 4 · Загрузка в заказ

Кнопка **«Загрузить данные в приложение»**:
- добавляет строки в **текущий** заказ (не схлопывая дубли);
- проставляет qty и price;
- не проводит заказ автоматически;
- пишет audit: кто, сколько строк, шаблон маппинга.

Кнопка **«Создать на основании»** (как на скрине):

- создаёт черновик прихода (§6)

## 6. Приход на основании заказа (склад)

### 6.1. Заменить текущее поведение

**Сейчас:** «Новый приход → на основании заказа» → `POST /supply/inbound-request` → задание складу + скан марок.  
**Нужно (основной путь со скринов):** создать **черновик приходной** со всеми строками заказа.

Скан/марки — **второй**, опциональный путь (не удалять, переименовать: «Оприходование по маркам»).

### 6.2. Создание черновика

Входы:
1. Заказ → «Создать на основании» → Приходная накладная  
2. `/in` → «По основанию» → заказ (тот же API)  
3. API: `POST /warehouse/inbound/from-order` `{ supplier_order_id, warehouse_id?, copy_prices?: false }`

Правила заполнения:
- `source_supplier_order_id` = id заказа  
- поставщик, организация из заказа  
- `supply_number` = invoice_number заказа (если есть)  
- comment = `Основание: заказ {number}` + опционально текст  
- строки: **каждая строка заказа → строка прихода** (дубли сохраняются)  
- qty = qty заказа (стартовый план; склад правит факт)  
- price = **0** по умолчанию (`copy_prices: false`); при `true` — цена из заказа  
- `posted = 0`  
- baseline для расхождений = **снимок строк заказа** (не «что сейчас в черновике после правок»)

### 6.3. Работа склада в черновике (уже частично есть)

- править qty, удалять/добавлять строки  
- размещение по ячейкам  
- редактировать комментарий  
- **Сохранить** / **Оприходовать**  
- при проведении: остатки + ячейки + **акт о расхождениях**, если факт ≠ baseline заказа  
- обновить статус заказа → `partial` / `received`  

### 6.4. Несколько приходов на один заказ

Разрешено (частичные поставки).  
Анализ суммирует **все проведённые** приходы с `source_supplier_order_id = этот заказ`.

## 7. Отчёт «Анализ заказа поставщику»

Замена заглушки. Эталон — скрин 1С.

### 7.1. Колонки

| Группа | Колонка | Смысл |
|--------|---------|--------|
| | Номенклатура, ед. | название + артикул |
| **Поступление** | **Заказано** | Σ qty строк заказа (по product_id / артикулу — см. ниже) |
| | **Получено** | Σ qty проведённых приходов по заказу |
| | **Осталось получить** | Заказано − Получено; **может быть < 0** (излишек) |
| Размещение (MVP опционально) | Поступает на склад / в резерв | если нет данных — скрыть в MVP |

### 7.2. Агрегация строк

Два режима (переключатель):
1. **Как в заказе** — построчно (дубли не схлопывать) — ближе к документу  
2. **По номенклатуре** — сумма qty по `product_id` — ближе к 1С-анализу  

По умолчанию: **по номенклатуре** (как на скрине анализа).

### 7.3. UI

- Открыть из вкладки **Отчёты** заказа  
- Журнал отчётов закупок: выбрать заказ / период / поставщик  
- Кнопка **Сформировать**  
- Подсветка строк с Осталось ≠ 0  
- Печать / Excel — желательно в той же волне  

### 7.4. API

`GET /purchases/supplier-orders/:id/analysis`  
→ `{ order, lines: [{ product_id, sku, name, qty_ordered, qty_received, qty_remaining, receipts: [...] }] }`

## 9. Цены — явное разделение (из скринов + прошлых указаний)

| Документ | Цены |
|----------|------|
| Заказ поставщику | **Обязательны** при проведении (закуп с доставкой из пакинга) |
| Приход по факту | **По умолчанию 0**; не блокировать проведение из‑за нулевой цены |
| Свободный приход без заказа | Можно требовать цену (текущее поведение) или тоже 0 — **не ломать**; отдельный флаг |
| Розничные цены карточки | Не трогать при импорте заказа, если режим «минимальная карточка»; в режиме «клон» — копировать |

## 10. Что **не** входит в это ТЗ (чтобы не расползтись)

- Полный OData-обмен с 1С  
- Счета на оплату поставщику, СФ, ГТД, доп. расходы, доверенности  
- Комиссионные закупки  
- Автооплата / банк по заказу  
- Обязательные Data Matrix на каждую штуку при приходе «по факту qty» (скан-путь остаётся опциональным)  
- Перенос всех thin-заглушек меню закупок

## 12. Критерии приёмки (чеклист по скринам)

### Закуп
- [ ] Из таблицы (копипаст) заливается **артикул + qty + цена + сумма** в заказ  
- [ ] Настройки колонок сохраняются / шаблон  
- [ ] Сводка: получено / сопоставлено / будет создано / невозможно  
- [ ] 3 отсутствующих артикула создаются (или минимально, или клоном)

## 14. Открытые решения (зафиксировать до кода)

1. **«Провести» vs «Провести и закрыть»:** оба ведут в `in_transit` или только «и закрыть»?  
   **Предложение ТЗ:** оба → `in_transit` (для склада важен именно этот статус).  
2. Копировать ли цены заказа в приход по умолчанию?  
   **Предложение:** нет (0), чекбокс «перенести цены закупки».  
3. Префикс `MR` для коротких `AE/AA` — всегда авто или спрашивать?  
   **Предложение:** авто + показать в превью сопоставления «AE12679 → MRAE12679».  
4. Минимальная карточка vs полный клон при «создавать новые»?  
   **Предложение:** если в импорте есть **старый артикул** — полный клон; иначе — минимальная + предупреждение.
