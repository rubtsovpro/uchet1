# Концепция модуля аналитики и атрибуции
**Проект:** Учёт №1 / MRAER («Альтернатива 1С») · `1c.pnevmopodveska1.ru`  
**Дата:** 18.07.2026  
**Статус:** концепция и план внедрения v1; внешний Roistat на период внедрения сохраняется  
**Связанные материалы:** бриф карты экранов; ответы В2 / В3 основного ТЗ (Roistat, SLA)

**Назначение вкладки:** зафиксировать цели, границы, источники данных, этапы, KPI и критерии приёмки собственного контура управленческой аналитики внутри Учёта №1 — без подмены операционного ТЗ склада и без требования полной замены внешнего Roistat в v1.

---

## 1. Назначение продукта

Собрать в Учёте №1 рабочий контур управленческой аналитики: **звонки + сделки + деньги / отгрузки** — для ежедневных вопросов владельца и РОПа без обязательного ухода в сторонний кабинет.

**Закрывает v1**

- Объём звонков за день / неделю: принятые, пропущенные, средняя длительность, ответственный.
- Связка «звонок ↔ сделка ↔ (при наличии) оплата / отгрузка».
- Сводки по воронкам AmoCRM и по операционному контуру склада (опора на существующие `/ops`, `/income`, сделки Amo).
- Табличные отчёты с фильтрами и выгрузкой CSV.

**Не является целью v1**

Полная функциональная замена Roistat «один в один» (UTM, мультиканальная атрибуция, динамический коллтрекинг с подменой номеров, кабинеты рекламных площадок). Внешний Roistat (ориентир порядка 80 тыс. руб./мес.) **не отключается** до отдельного решения заказчика. Собственный контур наращивается параллельно. Ориентир на зрелый «свой Roistat» — не раньше ноября 2026 (ответ В2 основного ТЗ).

## 2. Границы и контекст данных

| Уже есть в продукте | Где | Использование в аналитике |
|---------------------|-----|---------------------------|
| Дашборд склада | `/ops`, API `/ops/dashboard` | KPI отгрузок, очередь, блок «не оплачено» |
| Зеркало «Доход» | `/income`, API `/ops/income`, таблица `income_mirror` | Деньги / реализация рядом со сделками |
| Сделки и воронки Amo | `/deals`, `/pipelines`, sync `/crm/deals/sync` | Ядро склейки и вороночных отчётов |
| Задания склада | `/warehouse/tasks` | Статусы сборки → выдача как операционный факт |
| Пункт меню «Аналитика» | CRM / Склад (заглушки «Отчёты») | Заменяется на рабочий раздел |

**АТС:** МегаФон.  
**Звонки:** уже фиксируются в AmoCRM.

**Жёсткое правило v1:** звонки загружаются **из AmoCRM** (контур amo1c / Amo API). Прямой API Мегафон в v1 **не** подключается. Прямой Мегафон — отдельный этап, если Amo не отдаёт необходимые поля (запись разговора, точный статус линии и т.п.).

## 3. Источники данных

### 3.1. AmoCRM (основной для v1)

- Сделки, воронки, статусы, ответственные — уже синхронизируются в `crm_deals` / `crm_pipelines`.
- **Звонки / события звонков** — новый поток: notes/events типа call (направление, длительность, ссылка на запись при наличии в Amo, связь с контактом / сделкой / ответственным).
- Контакты и телефоны — только в объёме, необходимом для склейки (без отдельного ТЗ по карточкам контрагентов).

### 3.2. WMS / Учёт №1

- `warehouse_tasks` и события статусов — операционная воронка склада.
- `income_mirror` — факт дохода (зеркало; дублирование записи из контура 1С без необходимости не выполняется).
- `deal_payments` — статусы оплаты по сделкам (конверсия «сделка → оплата»).

### 3.3. МегаФон

- В v1 — **только через Amo** (источник правды для менеджера на текущем этапе).
- Позже (v2+): прямой API / CDR / расширение коллтрекинга — при недостаточном качестве данных Amo.

### 3.4. Внешние рекламные источники

- Не в v1. UTM, Директ, Авито, органика, метки Roistat — этап «полный Roistat» (§9).

## 4. Экраны UI

Раздел меню Учёта №1 верхнего уровня: **«Аналитика»** (не внутри CRM-заглушек).

| Экран | URL | Назначение |
|-------|-----|------------|
| Обзор | `/analytics` | KPI дня / периода: звонки, сделки, доход, отгрузки |
| Звонки | `/analytics/calls` | Журнал звонков, фильтры, склейка со сделкой |
| Сделки и воронка | `/analytics/deals` | Сводки по воронкам / статусам (поверх синхронизированных сделок) |
| Склейка | `/analytics/links` | Таблица «звонок → сделка → оплата / отгрузка» |
| Операционный день | `/analytics/ops` или deep-link на `/ops` | Без дублирования складского дашборда: ссылка + виджеты KPI |

**Роли**

- Владелец / admin / РОП — полный доступ.
- Менеджер — свои звонки / сделки (фильтр по `responsible`); чужие детализации — по согласованной модели прав.
- Кладовщик — раздел не требуется (остаются `/ops` и задания).

**UX v1 (минимум)**

- Период: сегодня / 7 / 30 / произвольный диапазон.
- Фильтры: ответственный, направление звонка, «есть / нет сделка», воронка.
- Переход из строки звонка в карточку сделки (`/deals/:id`) и/или `amo_url`.
- Кнопка «Обновить из Amo» (инкрементальный sync звонков).
- Экспорт CSV по текущему фильтру.

## 5. Сущности и таблицы

Новые сущности в SQLite WMS (рабочие имена).

### 5.1. `crm_calls`

Журнал звонков, нормализованный из Amo.

| Поле | Смысл |
|------|--------|
| `id` | PK (стабильный id из Amo / составной ключ) |
| `amo_note_id` / `amo_event_id` | Идентификатор в Amo |
| `direction` | `in` / `out` |
| `status` | answered / missed / busy / unknown (маппинг из Amo) |
| `started_at` | Начало |
| `duration_sec` | Длительность |
| `phone` | Номер (нормализованный) |
| `responsible_user_id` | Кто принял / совершил |
| `deal_id` | Сделка Amo, если привязана |
| `contact_id` | Контакт Amo (если есть) |
| `recording_url` | Ссылка на запись, если Amo отдаёт |
| `raw_json` | Усечённый сырой фрагмент для отладки |
| `synced_at` | Момент синхронизации |

Индексы: `started_at`, `deal_id`, `responsible_user_id`, `phone`.

### 5.2. `analytics_deal_call_link` (таблица или VIEW)

Явная склейка при нескольких звонках на одну сделку:

- `deal_id`, `call_id`, `link_type` (`amo_native` \| `phone_match` \| `manual`), `confidence`, `created_at`.

**Правила склейки v1**

1. Если в событии Amo уже есть `deal_id` — принимаем (`amo_native`).
2. Иначе — сопоставление по нормализованному телефону с `crm_deals.buyer_phone` / контактом в окне ± N дней (по умолчанию 14) — `phone_match`, с оценкой уверенности.
3. Ручная привязка в UI — v1.1; не блокер приёмки v1.

### 5.3. Существующие таблицы (без дублирования)

- `crm_deals`, `crm_pipelines`, `crm_pipeline_statuses`
- `income_mirror`, `deal_payments`, `warehouse_tasks`

Агрегаты дашборда: SQL on the fly либо лёгкая `analytics_daily_stats` (дата × метрика) при росте нагрузки. На старте — без материализации.

## 6. API

Префикс: `/api/analytics/...` (auth + роль).

| Метод | Путь | Назначение |
|-------|------|------------|
| GET | `/analytics/overview` | KPI: звонки, пропущенные, сделки, доход, отгрузки |
| GET | `/analytics/calls` | Список звонков (пагинация, фильтры) |
| GET | `/analytics/calls/:id` | Карточка звонка + связанные сделки |
| GET | `/analytics/deals-summary` | Сводки по воронкам / статусам за период |
| GET | `/analytics/links` | Строки склейки звонок–сделка–оплата/отгрузка |
| POST | `/analytics/calls/sync` | Инкрементальная выгрузка звонков из Amo (паттерн CLI amo1c, аналогично экспорту сделок) |
| GET | `/analytics/export.csv` | CSV по типу отчёта и тем же фильтрам |

**Синхронизация**

- Скрипт в контуре amo1c: экспорт call-notes/events → JSON → upsert в WMS.
- Cron: каждые 5–15 минут + кнопка в UI.
- Rate-limit Amo соблюдается (паузы в amo1c уже применяются).

Существующие `/ops/*` и `/crm/deals*` не изменяются контрактно; аналитика их читает, не подменяет.

Ядро Э1 склада не блокируется. Пакет мониторинга / звонков — после стабилизации Э1; ориентир старта разработки API — **с 01.09.2026** (ответ В3).

## 8. Критерии приёмки v1

1. В меню Учёта №1 есть рабочий раздел **«Аналитика»** (не disabled-заглушка).
2. Звонки за выбранный период видны в журнале; по выборке одного рабочего дня расхождение с Amo по количеству **≤ 5%** (расхождения документируются: тип события, фильтр «только с длительностью» и т.п.).
3. Не менее **80%** звонков с номером или `deal_id` связаны со сделкой правилами v1 **либо** явно помечены как «без сделки».
4. На обзоре доступны KPI: всего звонков, пропущенные, сумма / кол-во из `income_mirror` за период, отгрузки / очередь со склада (из ops).
5. Есть экран склейки «звонок — сделка — оплата или отгрузка (если есть)».
6. Sync звонков работает по кнопке и по cron; прямой API Мегафон **не** используется.
7. CSV-выгрузка журнала звонков работает.
8. Документация: данный файл + короткий runbook (как sync, как читать расхождения).
9. Без необходимости не затронуты: legacy-потоки склада, карточка контрагента, сторонние планы по телефонам контрагентов.

## 9. Вне scope v1 (полный Roistat и смежное)

| Тема | Почему позже |
|------|----------------|
| Прямой API Мегафон / сырой CDR | В v1 достаточно Amo; меньше точек отказа |
| Динамический коллтрекинг, подмена номеров | Классика Roistat; отдельный проект и бюджет |
| UTM, client_id, мультиканальная атрибуция | Требуются сайты / лендинги и разметка |
| Кабинеты Директ / Авито / VK Ads | Отдельные интеграции и токены |
| Сквозная ROI-модель «реклама → звонок → оплата» с точностью Roistat | После стабильных звонков + сделок + оплат |
| ИИ-разбор записей звонков, скрипты продаж | Отдельный AI-пакет |
| Полное отключение внешнего Roistat | Только решение заказчика; до ноября не цель |
| SLA / алерты Telegram по зависшим сделкам | Пакет B / ответ В3; не блокер приёмки аналитики v1 |
| Зеркало всех Google Sheets «1-в-1» | Вне аналитического MVP |

## 10. Допущения и риски

**Допущения**

- Качество полей звонка в Amo определяется связкой МегаФон ↔ Amo; отсутствие длительности / записи фиксируется в runbook как limitation, журнал при этом не блокируется.
- Эталон сверки v1 — **AmoCRM + Учёт №1**, не внешний Roistat.
- Инкрементальный sync по `updated_at` / id; полная выгрузка при каждом цикле не выполняется.

**Риски**

- Нормализация телефонов (+7 / 8 / без кода) критична для `phone_match`.
- Rate-limit Amo при ошибках окна синхронизации может давать лаги журнала.
- Параллельное существование внешнего Roistat и собственного контура — возможны расхождения цифр; для приёмки v1 это ожидаемо и документируется.
